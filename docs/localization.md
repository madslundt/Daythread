# Interface localization

Daythread currently ships English (`en`), Danish (`da`), German (`de`), Spanish (`es`), French (`fr`), Norwegian Bokmål (`nb`), and Swedish (`sv`) interface text in the web app and iPhone app. **Interface language** is a device preference under Settings → Appearance. **System language** follows the first supported browser or iPhone language, matching regional variants such as `es-MX` and `fr-CA` to their base language and `no-NO` to Norwegian Bokmål; a chosen language overrides it on that device. This preference is independent of transcription routes, transcript translation targets, and the language of generated recaps. Recordings, names, transcripts, and model responses stay in their original language.

## Contribute a translation

1. Add the language code to `interfaceLanguages` in `src/web/src/i18n.ts`, import a matching JSON catalog, and add it to `catalogs`. Keep the English text in `src/web/src/locales/en.json` as the source key. Copy every key into `src/web/src/locales/<code>.json` and translate its value. Keep brand names, API names, URLs, and technical identifiers intact. The English source text is the runtime fallback when a translation is missing.
2. Add `src/ios/DaythreadApp/<code>.lproj/Localizable.strings` and `InfoPlist.strings` with the same keys as the English files. Translate the values, preserving format placeholders and punctuation needed by SwiftUI. The latter file covers system permission prompts. Add the language to `AppLocalization.languages` in `src/ios/Sources/OmiCore/AppLocalization.swift` to expose it in the Interface language picker (which uses each language’s self-name). Run `xcodegen generate --spec src/ios/project.yml --project src/ios` so the new resources appear in the checked-in Xcode project.
3. Run `python3 scripts/check_locales.py`, `npm --prefix src/web test`, and `npm --prefix src/web run build`. For iPhone changes, also run the simulator build in [operations](README.md#iphone-companion). Check the main screens at a narrow width and on an iPhone simulator, including long labels, buttons, alerts, accessibility labels, dates, and plural wording.

The five additional catalogs were initially machine translated locally, with interface terminology reviewed. Native-speaker review is welcome, especially for nuanced technical descriptions. The shipped apps read static catalogs and make no translation-service requests for interface text.

## Add or change interface text

For web copy, write an English source phrase in a component as `t("Save preferences")`, then add the identical key to `en.json` and a translation to every other JSON catalog. Use `t()` only for interface text: never wrap route names, HTML roles, CSS classes, IDs, API values, or user and model content. For text with changing values, use `t("{count} recordings", { count })` and preserve the placeholder name in every translation. Translate complete sentences rather than joining fragments. Date display helpers in `src/web/src/format.ts` and `calendarDates.ts` use the selected interface locale; date arithmetic and the backend timezone remain separate.

For native interface copy, use `L10n.text("Settings")` (the app alias for `AppLocalization`). Interpolation produces stable named placeholders: `L10n.text("Imported \(count) recordings")` uses the catalog key `Imported {value0} recordings`. Keep placeholder names intact; translations may reorder them. `L10n.key(value)` translates known dynamic interface labels and server messages at display time. Leave user names, transcripts, model responses, IDs, and URLs untouched. Views observe the interface locale so a language change updates the current screen without resetting navigation or drafts.

Use `source("…")` in web module constants and `L10n.source("…")` for native model messages that must remain in the source language until displayed. Translate the resulting value at the UI boundary with `t(value)` or `L10n.key(value)`. This keeps stored provenance and API values stable when the interface language changes. For protocol states, add the code and its English display label to `config/interface-labels.json`, add `status.<code>` to every catalog, and display it with `statusLabel(code)` / `L10n.status(code)`. Never send the translated label back to the API.

Backend-owned setting labels, descriptions, notices, and error templates are inventoried by `scripts/localization_server.py` and shared by both clients. Add their English keys and translations to both catalogs when changing backend copy. Known message templates are matched at display time; interpolated parameters remain verbatim. Provider diagnostics without a known template remain in their original language.

## Coverage checks

`python3 scripts/check_locales.py` checks catalog parity, nonempty translations, named placeholders (including repeated occurrences) and native format specifiers, untranslated English sentences, native permission descriptions, backend-owned copy, and protocol display labels. It also verifies that web and iPhone language registrations match every catalog and that the Xcode project includes every supported locale. The source scan covers TypeScript/TSX and Swift files for interface text that bypasses the localization helpers. Run it after installing web dependencies (`npm --prefix src/web ci`).

Intentional technical strings belong in `config/localization-exemptions.json`, with a reason. Keep exemptions narrow: a URL, storage key, regex, or protocol token should be exempt; visible interface copy should be localized. The checks cannot judge translation quality or identify every possible dynamic string, so also review errors, loading and empty states, counts, accessibility labels, system permission prompts, and server settings in context. Translate complete singular/plural phrases and verify long labels at a narrow width.
