# Official Omi app audio forwarding

An optional receiver is implemented at `POST /v1/integrations/omi/audio`. It accepts official-format PCM and queues the same local transcription/archive pipeline used by native capture. Playback, Rewind, diary, search and cited chat use the resulting recordings. Native iPhone capture and manual hosted transcript imports remain available.

**Network finding, verified against upstream on 2026-10-16:** the official app configures this integration, but current upstream delivers the HTTP POST **from Omi’s backend**, not directly from the phone. Its delivery code resolves and rejects private, loopback, link-local and shared-address-space destinations. A phone reaching home-core on LAN or a private VPN is therefore insufficient for the stock hosted service. This implementation does not deploy an ingress, open a tunnel, change a firewall, or expose the archive.

The receiver works on a private LAN/VPN with a compatible sender that actually has that route. For the hosted official service, proceeding requires an independently configured public HTTPS ingress restricted to this POST endpoint, or confirmation of a different supported delivery mode from Omi. Do not expose the existing unauthenticated archive API/UI. Until a sender can reach this receiver, configuring the official app alone cannot complete the intended pendant workflow.

## Verified upstream contract and limits of the evidence

Reviewed source revision [`35a270d5c422828a709057f5877427c51b56ebd2`](https://github.com/BasedHardware/omi/tree/35a270d5c422828a709057f5877427c51b56ebd2). This is source evidence; the installed App Store build/server deployment can differ.

| Evidence | Finding |
|---|---|
| [Audio Streaming guide](https://docs.omi.me/doc/developer/apps/AudioStreaming) | POST, `application/octet-stream`, signed PCM16 little-endian mono; `sample_rate` and `uid` query parameters. Settings → Developer Mode → Realtime audio bytes has URL and Every x seconds controls. |
| [Developer mode provider](https://github.com/BasedHardware/omi/blob/35a270d5c422828a709057f5877427c51b56ebd2/app/lib/providers/developer_mode_provider.dart) | Saves URL/interval and enablement through the official backend. No custom Authorization/header editor is provided for this webhook. |
| [Backend audio sender and retry helper](https://github.com/BasedHardware/omi/blob/35a270d5c422828a709057f5877427c51b56ebd2/backend/utils/webhooks.py#L509) | Appends/replaces `sample_rate` and `uid`, preserving other URL query values. Sends raw PCM with Content-Type and a generated `Idempotency-Key`, stable within its retry loop. Sends at most one second of PCM per POST, including shorter final fragments, even when the configured interval buffers more audio. Per-UID locking serializes sends within that process. |
| [Webhook HTTP client](https://github.com/BasedHardware/omi/blob/35a270d5c422828a709057f5877427c51b56ebd2/backend/utils/http_client.py) | Delivery rejects private destinations and does not follow redirects. This is a server network path. |
| [Pusher audio queue](https://github.com/BasedHardware/omi/blob/35a270d5c422828a709057f5877427c51b56ebd2/backend/routers/pusher.py#L570) | Sends buffered PCM onward from backend processing. Capture timestamps available inside that pipeline are not included in the developer HTTP contract. |

The guide explicitly documents **DevKit 1 v1.0.2 at 8 kHz**, **DevKit 1 v1.0.4+ at 16 kHz**, and **DevKit 2 at 16 kHz**. Modern app/backend source also contains Omi/OpenGlass BLE and Opus decoding routes, but that is not proof that every consumer model, firmware, transcription mode, or installed app build emits this webhook. Consumer pendant acceptance is pending; the user’s pendant has not arrived. This receiver supports 8 and 16 kHz decoded PCM only. It does not accept BLE framing, Opus, stereo, a WAV file, or an arbitrary upstream sample rate. If the purchased device produces another rate, inspect its actual contract before adding a converter.

Current upstream retries transient failures with default delays of 1, 5 and 30 seconds (configurable upstream); most 4xx failures are deterministic and stop retries, while 408 and 429 remain retryable. Circuit breaking, failure tracking and auto-disable can stop delivery. Source contains a dead-letter facility, which does not establish eventual replay or an operator-accessible recovery guarantee. Older/different deployments may omit delivery keys or behave differently.

## First use

1. Build and run home-core and your local STT/LLM services using the [installation guide](../README.md#installation). Configure their URLs/models in `.env`. Keep one backend process per archive, persistent storage and `OMI_WORKER_ENABLED=true`. Check `/v1/status`; healthy HTTP alone does not test model connectivity.
2. Generate a random token with `uv run python -c 'import secrets; print(secrets.token_urlsafe(32))'`. Save it as `OMI_AUDIO_FORWARDING_TOKEN` in the server’s `.env`; keep that file private. Restart the backend. Do not reuse an inference or Omi developer key. The receiver starts disabled; enable **Settings → Omi connection → Official app audio forwarding → Enable audio receiver**. Alternatively set `OMI_AUDIO_FORWARDING_ENABLED=true` before first run. Saved runtime enablement overrides the environment default; use the UI to disable it again.
3. Open `http://<home-core-LAN-address>:8787` in Safari on the phone (allow local-network access), or use the server’s private VPN address. This tests access to the archive/UI and native capture path. Keep the machine awake and permit TCP 8787 only on the intended private network. **It does not test reachability from Omi’s hosted sender.** Establish the sender route described above before expecting official deliveries. This task leaves that network setup to the operator and has not exposed anything.
4. In this project’s **Settings → Omi connection**, enter the origin reachable by the actual sender to obtain a URL template. Privately replace the placeholder token in the official app with the server token. Example template: `https://<receiver-host>/v1/integrations/omi/audio?token=REPLACE_WITH_SERVER_TOKEN`. Do not supply `sample_rate` or `uid`; upstream adds them. Use the exact path, without a trailing slash. No bearer header or Omi API key is needed by this receiver. The URL, including this narrowly scoped secret, is stored in the official app/backend configuration; it is not a cloud-free credential path.
5. In the official app go to **Settings → Developer Mode → Realtime audio bytes**, save the URL and **Every x seconds = 10**, and enable its switch. Some builds label the section Audio bytes/Developer. A ten-second interval can produce a burst of one-second POSTs; it does not guarantee one ten-second request. Short fragments may split speech and reduce STT quality; changing the buffering interval may not change actual POST duration. Validate recognition on the real device. Keep normal official capture connected and active. This receiver cannot enable BLE capture remotely.
6. When hardware is available, speak: “The test parcel arrives Friday at noon.” Wait at least the interval plus network/transcription time. In this project’s Settings, verify the accepted count increases, **Last new audio received** changes, and inspect any receiver failure. This proves delivery of those chunks only. It does not establish pendant connectivity, uninterrupted capture or model success.
7. Open **Rewind**, choose a window around server receipt, expand the sources and play each recording. Confirm intelligible speech and plausible sample-derived duration. Check the transcript/test phrase and that state reaches `done`; search for “parcel”, generate that day’s diary and ask when the parcel arrives. Inspect the cited source/audio. Webhook source details explain estimated timing. For bursts/overlap, individual source playback preserves every chunk; the combined Rewind timeline is an estimate.

You can validate the receiver before the pendant arrives with a synthetic official-format request from a trusted LAN/VPN client. Create `/tmp/omi-test.pcm` as raw mono signed PCM16 little-endian at 16000 Hz, then POST its bytes with `Content-Type: application/octet-stream`, `uid=test-user`, `sample_rate=16000` and the configured `token` query value. Include a fresh UUID `Idempotency-Key` and resend that same request to verify the same local ID and `duplicate=true`. This checks transport, conversion, playback and queueing; synthetic tones/silence do not verify speech recognition or physical capture. Tests use isolated temporary archives and mocked model responses.

## Receiver behavior

- **Validation:** disabled by default; requires a 32–128-character URL-safe random server token. Constant-time comparison; duplicate token query fields are rejected. Authenticated requests require exactly one valid UID (1–128 ASCII letters/digits/underscore/hyphen) and sample rate, uncompressed octet-stream, a nonempty even-length PCM body, and at most 120 seconds/4,000,000 bytes (whichever is smaller). Both declared and streamed lengths are checked. At 16 kHz the duration ceiling is 3,840,000 bytes; at 8 kHz it is 1,920,000 bytes. Arbitrary even bytes cannot prove the sender really sent mono PCM rather than another format.
- **Acceptance:** at most four bodies/persistence operations in flight, a 15-second body timeout, 429 when busy. No STT/LLM runs on the request path. 16 kHz PCM gets a WAV header; 8 kHz gets deterministic twofold linear upsampling to the archive’s 16 kHz mono PCM16 boundary, preserving duration/pitch. Input sample rate/byte count/hash and output rate are recorded in `source_metadata`. Sample duration, not configured interval, sets bounds.
- **Durability:** write a private temporary WAV, fsync, atomically rename to a server UUID path, fsync its directory, then commit the queued audio row, provenance and receipt in one SQLite FULL-synchronous transaction. Only then return HTTP 200 with local ID, original receipt instant (`accepted_at`), duplicate flag and timing basis. `accepted_at` records body receipt for the accepted delivery, not precise fsync/commit completion time. Disk/database failure returns sanitized 503 with no accepted job. A crash before commit may leave an unreferenced file; it never creates a successful acknowledgement. Do not remove archive files while the backend runs. Once accepted, the existing worker retries inference and recovers interrupted jobs after restart, independently of the sender.
- **Identity:** `source_kind=omi_audio_webhook`, `source_id=<supplied uid>`, plus a namespaced hash of the UID as `device_id`. UID describes an upstream account supplied by a token holder, not authenticated Omi origin, a physical device, speaker or local person. Two accounts stay separate. Multiple physical devices under one UID cannot be distinguished by this contract. No physical device ID, firmware, session ID or sequence number is invented.
- **Times and boundaries:** `received_at`/`ended_at` equal server UTC time after the full body arrives; `started_at` subtracts PCM duration. `timestamp_basis=receipt_end_estimate` travels with public source records and source-kind reaches local summary/chat prompts. These are indexing estimates, not capture times. There is no reliable reordering, latency correction, or inference of real gaps. Requests remain independent; no concatenation across POSTs, UIDs or sample-rate changes. Delayed batches/retries can overlap or appear on the wrong calendar day. Concurrent order follows receipt/acceptance, not capture. Separate individual playback is authoritative; combined Rewind overlays by archive timestamp and later ordered rows overwrite overlapping samples, so it cannot reconstruct an original continuous stream from bursts/multiple senders.
- **Coverage:** playable/transcribed receipt estimates are reported separately from known capture intervals and do not remove unknown capture coverage. Last native capture time excludes webhooks. No server receipt is presented as a live pendant connection. Source bounds still determine Rewind/diary/date retrieval placement, with the disclosed uncertainty.
- **Duplicates:** when `Idempotency-Key` is provided (1–128 ASCII letters/digits/underscore/hyphen), `(uid, key)` identifies a delivery. A transactional receipt ledger returns the original ID for matching audio/rate across concurrency/restart; changed content/rate returns 409. Raw keys are hashed in the ledger. Tombstones survive source deletion/retention and backup, so keyed retries do not resurrect deleted audio; an acknowledgement then means previously accepted, not currently retained/playable. Without a key, every valid POST gets a fresh UUID, even for identical bytes. Content-only deduplication would incorrectly discard repeated speech/silence. Upstream replay under a new key can therefore duplicate content. Exact deduplication is not promised. Content-free receipt metadata/hashes remain after source expiry; retention does not purge this small retry ledger.
- **Pause/coexistence:** local capture pause rejects new webhook POSTs with 409 and does not turn off the official phone/cloud pipeline. Already accepted work continues. Native stable-ID WAV upload and hosted transcript import keep their own contracts; cloud import is transcript-only, keyed by conversation ID, and is never queued for STT. Importing a conversation also captured via webhook/native capture can yield duplicate evidence: there is no shared source ID to merge them safely. Prefer one active wearable capture app; concurrent BLE ownership is device-dependent. Official button semantics are not translated by this audio-only route.

## Endpoint access and network exposure

The URL token is necessary because this official configuration offers a URL, not configurable auth headers. It authenticates possession of a receiver credential, not an Omi signature. Keep it out of screenshots, browser address bars/history, issue reports and shared logs. The backend never returns it from settings/status or saves it in archive backups. Its middleware removes `token` from forwarding request query strings before routing/access logging, including malformed/disabled requests. A proxy, tunnel, load balancer or upstream server ahead of this middleware must independently omit/redact query strings and bodies; Omi stores the configured URL. Rotate the env token and update the official URL if disclosed.

The rest of this project’s API/UI still has no authentication. A public ingress must allow **only POST on the exact receiver path**, use a trusted HTTPS certificate, enforce body/time/concurrency limits and forward query strings plus `Idempotency-Key` intact to home-core. Return 404 for all other routes, including status, audio playback, settings, uploads and OpenAPI. Do not forward port 8787 publicly. Do not put an interactive login, redirect, or custom-header requirement on this one webhook: the sender cannot complete it. Keep backend administration/status on LAN/VPN. Use a separate origin rather than putting a receiver token in an archive URL.

For a compatible direct sender on a private network, LAN access or a private VPN with routing to home-core can suffice; prefer HTTPS or an encrypted VPN. For the current hosted official sender, **a phone-only VPN does not grant the Omi server access to your VPN** and its SSRF guard rejects private targets. No such public ingress has been created or tested here.

## Failure guidance and away-from-home behavior

| Observation | Action |
|---|---|
| Disabled / missing server token | Set the env token, restart, enable the receiver in Settings. Check saved runtime settings precedence. |
| No accepted chunks and no receiver error | Confirm sender route first; localhost/private DNS/LAN/Tailscale-only IPs do not work from the hosted sender. Check exact official saved URL, switch/interval, internet/BLE/capture mode and whether upstream disabled the webhook. Phone Safari reaching the UI is a different test. |
| 401 | Token missing/mismatched/duplicated. Replace privately in official settings; there is no bearer-header setup. Unauthorized traffic does not overwrite the authenticated failure diagnostic. |
| 415 / 422 / 413 | Check octet-stream raw PCM, 8/16 kHz mono, sample alignment and duration/byte limits. Avoid sending WAV/Opus packets. Reduce interval if your sender sends large bodies; source versions differ. |
| 409 | Resume local capture, or investigate changed content under a reused delivery key. Upstream may stop deterministic retries; resume and re-enable there if needed. |
| 408 / 429 / 503 | Timeout/load/disk/database failure: keep the same delivery key on retry. Check storage permissions/space and one-worker deployment. The sender’s finite retries can still be exhausted. |
| Accepted, pending/blocked or no transcript | Check worker enablement and local STT status, silence gate, model configuration and per-source errors. Playback and receipt do not prove recognition. Fix the cause and retry transcription on the source; do not resend with a new key. |

Last receipt/count persist through restart; sanitized last failure is only for the current backend process and can predate a later success. Counts include previously accepted sources that have since been deleted/expired.

Away from home the stock official app still needs its own supported capture and upstream connection, and its hosted sender needs a reachable ingress. The home archive can be browsed over a private VPN. Losing internet/BLE, killing/backgrounding the official app, switching capture modes, or making the receiver unreachable can cause missing delivery; this adapter adds no phone outbox, storage download, continuous-capture guarantee or offline replay. Native Daythread has a separate durable phone outbox for audio it actually received. Neither forwarding nor choosing local STT establishes that official app audio/transcripts avoid Omi’s cloud.

## Validation and hardware acceptance

Automated integration tests exercise 8/16 kHz official requests, signed sample values/duration, playable WAV, queued worker → search/Rewind/diary/cited chat, size/format/metadata/auth rejection, disk failure, concurrent senders/retries, restart, deletion tombstones, model retry, secret redaction and unchanged native ingestion. Existing hosted import tests cover its separate contract. Frontend checks cover status, failure and uncertain-timing presentation. Model responses are mocked; no claim of recognition quality follows.

Validation run on 2026-10-16: **426 backend tests passed**, including **35 focused receiver tests**; **47 frontend tests passed**; Ruff, TypeScript/Vite production build and `git diff --check` passed. Built assets were packaged into the backend. Playwright checked Settings on loopback-only `http://127.0.0.1:18879/#settings` at 1280×900 and 390×844: correct page/content, no framework overlay, no console errors/warnings, enable/disable persistence, new receipt status, no token in page, and no horizontal overflow. Actual Uvicorn access output omitted the query token. The temporary QA server was stopped.

The host’s installed `uv` (0.11.32) is below this repository’s required 0.13.1, so Python checks used the existing `.venv/bin/pytest` and `.venv/bin/ruff` directly. Node 26.8.1/npm 11.19.0 also predate the repository pins; frontend checks still passed. No version pins, dependencies, `.env` or user archive were changed by this receiver work. Full model quality and hosted ingress/physical delivery were not tested.

When the pendant arrives, record model/firmware/codec, phone OS/app version, selected official capture mode, interval and backend revision. Verify:

- Actual official format/rate and whether this device/mode emits requests; sender network origin and delivery keys in sanitized request diagnostics (never log the token/body).
- A five-minute timed speech recording: compare total sample duration, gaps, per-source intelligibility, test phrase transcription and cited diary/chat. Check burst/overlap behavior rather than assuming receipt time is capture time.
- Screen lock/background for an hour, calls, BLE disconnect, app restart, internet loss and receiver downtime; measure missing audio and any replay/duplicate behavior. Observe upstream auto-disable/re-enable after recovery.
- Two devices/accounts where possible; same-account sources cannot establish distinct device identity. Do not require simultaneous BLE capture apps to succeed.
- Receiver token rotation, actual ingress route isolation/TLS/log redaction if the operator later provisions one, and private archive access from home/away.

These physical and hosted delivery checks are pending. The feature is implemented and locally testable without the custom iPhone companion; stock hosted use additionally depends on a compatible device/mode and a sender-reachable endpoint.
